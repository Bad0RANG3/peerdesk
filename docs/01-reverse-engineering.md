# 网易UU远程 逆向分析报告

> 观测对象：网易UU远程（内部代号 **NRD**，即 NetEase Remote Desktop），
> 客户端版本 `4.48.0.5446`，构建日期 2026-11-16。
>
> 证据来源：二进制字符串与结构信息提取、运行期进程/服务/网络观测、配置与缓存分析、
> 官方 CLI 行为观察。报告只记录架构与产品行为，不包含账号凭据、设备明文码、
> 官方代码或可复用的私有资源。

## 1. 产品构成

网易UU远程不是单一窗口程序，而是一组常驻服务、渲染/媒体组件和驱动：

| 组件 | 观察到的职责 |
| --- | --- |
| `GameViewer.exe` | 主客户端。Qt5 应用壳叠加 WebView2 业务界面，承载登录、设备列表、连接码、会员与充值入口 |
| `GameViewerServer.exe` | 被控端后台进程，负责上线注册、接受控制请求、拉起会话和媒体组件 |
| `GameViewerService.exe` | Windows 服务宿主，名称 `GameViewerService`，以自动启动方式运行 |
| `GameViewerHealthd.exe` | 健康检查与进程守护 |
| `streamer.dll` | 媒体与传输核心，包含 ICE、DTLS-SRTP、QUIC/KCP、自研多路复用、FEC 和编解码调度 |
| `uuyc-cli.exe` | 官方命令行入口，暴露设备、状态、终端和诊断能力 |
| `uuyc-mux.exe` | 终端多路复用组件，面向远程 Shell 场景 |
| 音频、渲染与终端桥组件 | 虚拟声卡联动、渲染进程 IPC、ConPTY 远程终端桥 |

业务页面并不完整内置在客户端中：公开的本地页面主要是错误页、骨架页和桥接脚本，
实际业务界面由 **WebView2** 从服务端下发。这个结构让静态提取很难直接得到完整中文文案，
也意味着 UI 迭代可以脱离客户端发版。

### 1.1 内核驱动与系统集成

| 驱动 | 作用 |
| --- | --- |
| `GameViewerIddDriver` | 基于 IddCx 的虚拟显示器；配置中可见 2560×1440 等虚拟屏参数 |
| `ViGEmBus` | 虚拟游戏手柄，模拟 Xbox/DS4 设备 |
| `nevaudio` | 虚拟声卡，支持采集系统播放声音 |
| `uuycinput` / `uuycinputmf` | 虚拟键鼠 HID，降低游戏和受保护界面对普通注入的拦截 |

“虚拟显示器 + 虚拟键鼠 + 虚拟声卡”是 UU远程在高帧率、游戏兼容和分辨率控制上的关键。
它们都位于驱动层，不能由纯用户态 Qt 程序等价替代。

## 2. 运行期拓扑

```text
控制端 GameViewer.exe ── HTTPS/REST ──▶ 网易信令与业务服务
        │
        ├── P2P：UDP 候选交换、ICE、打洞
        │
        └── Relay：安全中继 / 代理中继

被控端 GameViewerServer.exe ── UDP 会话端口 ──▶ 控制端
        ▲
        └── GameViewerService.exe 守护
```

观测要点：

- 控制、房间、设备、会员等业务请求走 HTTPS；传输信令通过双向 RPC 通道完成。
- 媒体端口使用 UDP，打洞和媒体复用同一组本地端口，端口随会话变化。
- 客户端配置里能看到画质、自动画质、智能鼠标、窗口几何等每设备偏好。
- 编码能力缓存包含 H.264/HEVC、硬件/软件实现、最高 3840×2160、8/10 bit、
  4:2:0/4:4:4 等组合，并会按 GPU 能力禁用部分编码器。

## 3. 传输栈

`streamer.dll` 暴露的模块名和日志字符串可以较确定地还原传输分层：

1. **libwebrtc 底座**：ICE 控制器、`P2PTransportChannel`、packet socket、
   DTLS transport、DTLS-SRTP 和 SRTP filter。
2. **QUIC 与 KCP 共存**：ngtcp2 连接类、KCP 参数、QUIC/KCP 切换开关并存。
3. **自研复用层**：在 QUIC/KCP 之上做包复用、FEC 生成与恢复，并对不同网络质量切换策略。
4. **多档打洞**：CLI 中存在 `--disable-lite-punch`，说明打洞策略不是单一流程。
5. **中继商业化**：安全中继、文件高速中继与会员权益直接耦合；同时存在
   SOCKS5/HTTP 代理中继实现。

与 PeerDesk 的简化方案相比，UU远程的传输栈更接近“WebRTC 能力 + 自研可靠层 + 商业中继”
的组合，而不是单独一套私有 UDP 协议。

## 4. 服务端接口面

从二进制中可提取到 132 条 `/api/...` 路径。它们覆盖房间、分享、访客、传输信令、
设备、会员、云电脑、登录、版本和埋点，典型分组如下：

| 域 | 代表性能力 |
| --- | --- |
| 房间与会话 | 创建/加入房间、分享加入、按设备加入、重新拉取房间信息 |
| 远程协助 | 对方确认、控制/观看模式、取消协助 |
| 传输信令 | 双向 RPC 请求/响应、网络状态、回声服务 |
| 设备管理 | 设备列表、可控设备、重启、屏保、Wake-on-LAN |
| 会员与计费 | 权益、试用、充值卡、消费记录 |
| 云电脑 | 创建、开机、磁盘、排队、票据、流媒体配置、费用 |
| 登录 | 手机、二维码、UU 令牌、MuMu 令牌 |
| 版本与运营 | 更新、弹窗、活动、插件版本 |

产品逻辑上有三点值得注意：

1. P2P 能连通时是基础能力，打洞失败后的“安全中继”被包装为会员权益。
2. 云电脑按资源与时长计费，和普通设备远控是两套成本模型。
3. 远程协助提供“请求对方确认”和“仅观看/可控制”等授权差异。

### 4.1 官方 CLI 暴露的产品面

`uuyc-cli.exe` 提供 `version`、`status`、`user`、`device`、`cloudpc`、`echo`、
`assist`、`term`、`lterm` 等子命令，并保留设备 ID、设备列表、自定义连接码重置、
连接、码率限制、关闭轻量打洞和输入诊断等参数。

其中 `term`/`lterm` 与终端多路复用组件对应，说明远程终端是独立产品能力，
而不是远程桌面画面上附加一个命令行窗口。`input-diag` 则反映官方也把游戏输入兼容性
作为需要专门诊断的故障域。

## 5. 与 PeerDesk 0.9 的能力对照

PeerDesk 的目标是复现交互模型和自托管体验，不是复制官方实现。

| 能力 | 网易UU远程 | PeerDesk 0.9 |
| --- | --- | --- |
| 技术栈 | Qt5 应用壳 + WebView2 业务页 + 原生媒体/驱动组件 | C++20 后端 + Qt 6.8 Widgets 原生客户端 |
| 连接码 | 9 位数字，分组显示，支持自定义/重置 | 9 位数字，3-3-3 显示，可更换本机码 |
| NAT 穿透 | ICE、NAT 类型判断、多档打洞、商业中继 | 本地 IPv4 + STUN 候选、100 ms PUNCH、6 秒升级自托管 UDP 中继 |
| 加密 | DTLS-SRTP | X25519 + HKDF + 每包 AEAD，带重放窗口 |
| 视频 | H.264/HEVC，硬/软编，8/10 bit | GDI 抓屏 + Media Foundation H.264/JPEG，自适应质量、FEC、NACK、关键帧请求 |
| 虚拟显示器 | IddCx 虚拟屏 | 仅真实桌面显示器 |
| 输入 | 虚拟 HID，部分场景兼容性更好 | Win32 `SendInput`、绝对坐标、文本、滚轮和组合键 |
| 音频 | 虚拟声卡与完整音频链路 | WASAPI loopback、16 kHz 单声道、G.711 µ-law、上一帧冗余 |
| 文件 | 中继加速与会员权益 | 双向控制消息传输，24 KiB 分块，单文件 512 MiB 上限 |
| 剪贴板 | 文本、图片等 | 双向文本，单次 256 KiB |
| 多显示器 | 支持选择 | 支持枚举和切换 |
| 远程终端 | 官方 CLI + 终端多路复用 | 未实现 |
| Wake-on-LAN | 设备接口支持 | 未实现 |
| 自托管 | 仅官方服务 | 信令、STUN、中继均可自行部署 |

PeerDesk 目前明确没有虚拟显示器、虚拟 HID、远程终端、Wake-on-LAN 或远程 Shell。
Windows 视频已接入 H.264/JPEG 协商与编码器失败回退，但真实跨机画质、延迟、带宽、
硬件编码策略和长时间稳定性仍待验收；声音仍是 G.711，尚不能描述成 Opus 质量。

## 6. 对 PeerDesk 的设计启示

- **连接码要成为唯一低摩擦入口**。账号、设备列表和会员弹窗不应阻塞临时远控。
- **直连优先、中继兜底**。路径切换应自动发生，UI 只展示当前状态，不要求用户理解 NAT。
- **控制与媒体分离**。鼠标键盘和剪贴板需要可靠、有序；视频和音频可以丢包，再用 FEC、
  NACK 或冗余恢复。
- **握手字节必须稳定**。重发 HELLO 时要复用原始字节，否则双方 transcript 不同，
  会出现“握手完成但所有包都解不开”。
- **包序号与消息序号分离**。包头序号承担 AEAD nonce 和重放窗口，控制消息必须在载荷内
  使用独立序号。
- **弱网体验依赖策略而非单一编码器**。画质、帧率、关键帧和路径切换需要联动，
  不能让用户手动反复改设置。

## 7. 分析边界

本报告不包含官方账号、明文设备码、私有接口凭据或绕过授权的任何方法。
业务 UI 由服务端下发，未做 DTLS-SRTP 解密，因此中继阈值、码率算法等只能给出架构级判断。
真正的产品对齐仍以 PeerDesk 自己的跨机测试、弱网测试和长会话验收为准。
